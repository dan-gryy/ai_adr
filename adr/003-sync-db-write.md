# ADR 003: Синхронний запис повідомлень у БД перед розсилкою

## Контекст
У рамках реалізації Завдання 3 (Sequence Diagrams) для UC-01 "Відправка повідомлення" необхідно було визначити порядок взаємодії між TCP-сервером, базою даних (PostgreSQL) та клієнтами під час відправки нового повідомлення. 

## Альтернативи

1. **Асинхронний запис (Оптимізація Latency)**
   * *Опис:* Сервер миттєво розсилає повідомлення всім активним клієнтам, а запис у БД делегує фоновому процесу.
   * *Плюси:* Мінімальна затримка (latency) для користувачів.
   * *Мінуси:* Ризик втрати даних, якщо сервер впаде до запису в БД; складнощі з генерацією єдиного UUID без участі бази.

2. **Синхронний запис (Строга консистентність) — [ОБРАНИЙ ВАРІАНТ]**
   * *Опис:* Сервер спочатку робить `insertMessage` в БД, отримує згенерований `newMessageId`, і лише після успішної відповіді БД розсилає повідомлення клієнтам (loop).
   * *Плюси:* Гарантія збереження даних; єдине джерело правди для ID повідомлення.
   * *Мінуси:* Блокування на час виконання SQL-запиту (збільшує latency).

## Рішення
Обрано **Альтернативу 2 (Синхронний запис)**. Оскільки для MVP EchoLink важливіша надійність збереження історії чату та синхронізація повідомлень за єдиним ID. Sequence-діаграма для UC-01 тепер чітко відображає розсилку (`loop pushEvent`) строго після підтвердження від Database.
