# Намір
Створення концептуальної ER-моделі для чат-застосунку EchoLink.

# Сутності та атрибути
* **User:** id (UUID) PK, username, email
* **ChatRoom:** id (UUID) PK, name, created_at
* **Message:** id (UUID) PK, content, sent_at, author_id (UUID) FK, room_id (UUID) FK

# Зв'язки
1. User ||--o{ Message : "writes"
2. ChatRoom ||--o{ Message : "contains"
3. User }o--o{ ChatRoom : "participates in"

# Критерії прийняття
* [x] Модель знаходиться у 3NF.
* [x] Для всіх первинних і зовнішніх ключів використовується суворо тип `UUID` (не Int).
* [x] Зв'язок M:N між User та ChatRoom змодельований без фізичних сполучних таблиць.
* [x] Точний неймінг зовнішніх ключів у Message: `author_id` та `room_id`.



# Завдання 2: Вимоги та Use Cases (EchoLink)

## 1. Актори та їхні цілі
* **Користувач (User):** Авторизований учасник. Мета — обмінюватися повідомленнями.
* **Адміністратор (Admin):** Спадкує User. Мета — модерувати чат-кімнати.

## 2. Сценарії Gherkin для UC: "Відправка повідомлення"

**Сценарій 1: Успішна відправка повідомлення (Happy path)**
* **Given** користувач «Ілля» авторизований і є учасником кімнати «General»
* **When** він вводить текстове повідомлення «Привіт всім» і натискає Enter
* **Then** повідомлення зберігається та відображається в історії чату «General» усім активним учасникам

**Сценарій 2: Спроба відправки занадто довгого тексту (Alternate path)**
* **Given** користувач «Ілля» знаходиться в кімнаті «General»
* **When** він намагається відправити повідомлення довжиною 1500 символів
* **Then** система відхиляє відправку
* **And** відображає повідомлення про перевищення ліміту в 1000 символів

**Сценарій 3: Відправка повідомлення заблокованим користувачем (Error path)**
* **Given** користувача «Ілля» заблоковано в кімнаті «Dev»
* **When** він намагається відправити повідомлення в цю кімнату
* **Then** система відхиляє відправку та повідомляє про відсутність доступу

## 4. Нефункціональні вимоги (NFR)
* **NFR-P01 (Performance):** Час доставки повідомлення не повинен перевищувати **200 мс** при навантаженні до **500** активних користувачів.
* **NFR-S01 (Security):** Трафік повинен бути зашифрований за протоколом **TLS 1.2+**.
* **NFR-U01 (Usability):** Інтерфейс повинен коректно працювати на терміналах розміром не менше **80x24** символів.

## 5. Поза обсягом (Out of Scope)
* **Відправка файлів:** Не реалізується в текстовому термінальному MVP.

# Завдання 3: Діаграми взаємодії (Sequence Diagrams)

## 1. Прецедент, учасники та сценарії взаємодії
Деталізовано прецедент **«Відправка повідомлення» (Send Message)** у вигляді трьох окремих діаграм послідовності у файлі `diagram.md`:

* **Сценарій 1 (Успішна відправка):**
  * *Учасники:* `Client` (актор), `TCPServer`, `Database`, `OtherClients` (актор).
  * *Кроки:* `Client` викликає `sendMessage(chatId, userId, payload)` -> `TCPServer` перевіряє доступ через `verifyUserAccess(chatId, userId)` (отримує `true`) -> записує повідомлення через `insertMessage(chatId, userId, payload)` (отримує `messageId`) -> у циклі `loop` асинхронно надсилає `pushEvent` учасникам `OtherClients` -> повертає відправнику `200 OK (messageId)`.
* **Сценарій 2 (Перевищення ліміту довжини понад 1000 символів):**
  * *Учасники:* `Client` (актор), `TCPServer`, `Database`.
  * *Кроки:* `Client` викликає `sendMessage` -> `TCPServer` виконує перевірку `validateLength(payload)` -> спрацьовує блок раннього виходу `break` -> якщо довжина понад 5000 символів, у блоці `opt` викликається `logSuspiciousActivity` у `Database` -> `TCPServer` повертає `400 Bad Request`.
* **Сценарій 3 (Користувача заблоковано або немає доступу до кімнати):**
  * *Учасники:* `Client` (актор), `TCPServer`, `Database`.
  * *Кроки:* `Client` викликає `sendMessage` -> `TCPServer` викликає `verifyUserAccess(chatId, userId)` -> `Database` повертає `accessStatus = false` -> спрацьовує блок `break` -> `TCPServer` повертає `403 Forbidden`.

## 2. Критерії приймання (Acceptance Criteria)
* Для кожного з трьох сценаріїв Gherkin побудовано окрему діаграму послідовності.
* Помилкові виходи (коди 400 та 403) оформлені фрагментом `break`, а не `alt`.
* Розсилка іншим учасникам (`OtherClients`) виконується асинхронно `-)` у межах `loop` лише після синхронного підтвердження запису від `Database`.
* Смуга активації `TCPServer` охоплює обробку запиту, `Database` активується на час кожного запиту, а на акторів смуги активації не накладаються.
